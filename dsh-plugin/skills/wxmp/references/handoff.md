# 交接报告维护规则（改动插件就必须更新）

本插件根目录有一份 **`HANDOFF.md`**：它是插件的**活体状态卡**，写「现在是怎样」，
不是历史流水账。任何接手这个插件的人（或模型）开工第一件事是读它。

## 为什么它是硬规则

`HANDOFF.md` 里记着改代码时**必须连带改哪里**、**哪些错误形状不许退回去**、
**哪些结构约束一旦破了会静默失败**。这些知识只存在于报告里，代码本身不表达。
报告过期 = 下一手照错的说明书办事，比没有报告更糟。

## 改完代码必须跑

```powershell
cd "G:\AI PGRM\DSH\wxmp\dsh-plugin"
node tools/handoff-check.mjs
```

- 退出码 **0** = 报告与代码一致
- 退出码 **非 0** = 报告已过期，逐条打印「报告说 X / 代码是 Y / 改哪里」
- **非 0 不许宣称改动完成**，也不许为了让它是绿的而放宽检查项

## 必须更新 HANDOFF.md 的情形（任一命中）

1. 增删改 `OPERATIONS` / `UI_OPERATIONS` 的 op
2. 增删改任何错误码（`failure()` 的 code、`FAILURE_HINTS` 键、`article_delete` 系列）
3. 改返回结构形状（顶层字段、`data` 结构、`text` 语义）
4. 改槽位（槽位名、`panellist.id`、`order`、`main.key`）
5. 改路由（路径、`kind`、方法、白名单）
6. 改 `DEFAULTS` / `cordis.patch.yml` 的 config
7. 改持久化落点或文件名
8. 改超时 / 重试策略
9. 增删测试套件，或改动「回归锁」类断言
10. 改版本号
11. 文件地图行数偏差超 ±20%
12. 修复或新发现缺陷（同步「未闭环项」）

**只改文案 / 注释 / 排版** → 不必更新，但仍要跑一次校验。

## 校验器实际查什么（19 项）

它不是靠关键词匹配，而是**从代码里现取事实**与报告比对：

| 类别 | 具体检查 |
|---|---|
| 版本号 | 报告的 `\| 版本 \| **x.y.z** \|` vs `package.json` |
| op 数量 | 报告声明的数 vs `OPERATIONS` 实际长度 |
| op 覆盖 | 每个 `OPERATIONS` 项是否在报告里出现 |
| 幽灵 op | 报告里出现但代码没有的 op 名（排除宿主工具名） |
| buildArgv | `OPERATIONS` 每项是否都有 `case` 分支 |
| 本地 op | `LOCAL_OPERATIONS` 是否在报告写明 |
| 错误码 | `FAILURE_HINTS` 每个键是否在报告提过 |
| 配置一致 | `cordis.patch.yml` 的 config vs `DEFAULTS` 逐字 |
| 结构断言 | `failure()` 在 `runCli` 之前、只有一份、`promoteCliFailure` 被调用、`inject=[]`、exact+prefix 双路由、`panellist.id == main.key` |
| 引用完整性 | 报告提到的 8 个文件都存在 |
| 报告自身 | ≤ 400 行、含「维护规则」节、无把模糊措辞当结论 |
| 顺带守预算 | `SKILL.md` 字符数 + 220 ≤ 8192 |

## 报告怎么写

- 写现在，不写流水账；十节结构见 `HANDOFF.md` 本身
- **不许删「未闭环项」**来让报告看起来干净 —— 那是交接的核心价值
- 超过 400 行就把细节挪进 `docs/handoff-*.md`，在报告里留指路条

## 改报告时别改坏校验器

校验器是**契约**，不是装饰：

- 不许删断言来让它变绿
- 不许把 ERROR 降成 WARN
- 加新断言要保证**它能失败**（写一条恒真的断言等于没查，还给假信心）
- 校验器自己也要验证：故意改坏代码，确认它真的红
