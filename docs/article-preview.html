DSH 是什么：一个把 AI 变成能干活的操作台
快乐愿享
大模型会聊天，但不会替你改文件、跑命令、点按钮。DSH 补的就是这一段：把模型接上工具、技能和记忆，让它真的把事做完。

大多数人第一次用 AI 编程，都是这个体验：它答得很好，但活还是你自己干。

你问它"这段报错怎么修"，它给你三个可能原因。你说"那你帮我改"，它说"我无法访问你的文件"。你让它跑一下测试，它说"请你自行执行"。

问题不在模型够不够聪明，而在它有没有手。

DSH（DeepSeek Harness）解决的正是这一段——它不生产模型，它给模型装上手脚。

一、Harness 到底是个什么东西

Harness 这个词本意是"马具"。马有力气，但得套上挽具才能拉车。

放到 AI 里，模型是那匹马：它擅长理解、推理、生成，但它看不见你的硬盘、碰不到你的终端、记不住昨天聊过什么。Harness 就是那套挽具——把模型的"想"接到真实世界的"做"上。

具体装了三样东西：

  • 工具（Tools）：读文件、改代码、跑命令、开浏览器、调接口

  • 技能（Skills）：把"怎么做某件事"沉淀成可复用的操作手册

  • 记忆（Memory）：跨会话记住这个项目的架构、约定和踩过的坑

二、没有它和有它，差别在哪

举一个我这几天真实做的事。

没有 Harness 时：我说"帮我把这个项目做成 Windows 能用的版本"，得到的是一段建议——"你可以考虑用 Node 重写，注意路径分隔符差异"。

有 Harness 时，同一个请求变成了一串动作：

  1. 读远端仓库，搞清原项目的协议和架构

  2. 在本机找到微信开发者工具的安装位置（注册表里翻出来的）

  3. 写 WebSocket 客户端，直连工具暴露的自动化端口

  4. 第一次跑失败——cmd /c 把带空格的路径拆散了

  5. 换成生成 .cmd 包装器，绕开这个坑

  6. 真机跑通：启动、查看页面、点击、断言、截图

  7. 最后装成插件，我能在对话里直接调用

这七步里没有一步是"模型变聪明了"，全是"模型有手了"。

三、DSH 的几个关键设计

用下来，我觉得有意思的是这几点。

1. 它不是一个大程序，是一堆可插拔的零件

DSH 由几十个独立的包组成：文件系统、命令执行、会话存储、工具注册、Web 界面……每个都能单独替换。你在配置文件里排列组合，就能拼出完全不同的 Agent。

2. 插件即能力，装上就长出新器官

这是最实用的一点。同一个 DSH，装不同的插件就是不同的助手：

插件长出的能力
winpilot驱动微信开发者工具，操作小程序界面
wxmp写文章、排版、发到这个公众号
dsh-ghidra逆向分析二进制文件
办公套件读写 Word / Excel / PPT

我上面那个"Windows 版小程序自动化"，最后就是做成了一个插件。能力是可安装的，不是写死的。

3. 技能让经验能传下去

工具解决"能不能做"，技能解决"该怎么做"。

比如发公众号这件事，第一次我踩了一堆坑：正文样式被微信剥掉、图片必须走特定接口、标题超 32 字直接被拒。把这些写成 SKILL.md 之后，下次不用重新踩——Agent 会先读手册，再动手。

4. 记忆解决"每次都从零开始"

这个公众号的排版主题、你的偏好、这个项目的历史决策，都能存下来。下次开口不用重新交代一遍背景。

四、它适合谁

说实话，不是所有人都需要。

适合：手上有重复性工作、愿意把流程写成脚本的人。比如每天要发内容、要跑测试、要在几个系统之间搬数据。

不太适合：只想问个问题、要个答案的人。那种场景直接聊天就行，套一层 Harness 反而是负担。

一个判断标准：如果你的需求里出现"帮我做"，而不是"告诉我"，那才轮到 Harness 上场。

五、一个提醒

工具越强，越要清楚边界。DSH 这类系统的价值在于"能执行"，风险也在于"能执行"。

所以好的设计里一定有几道闸：

  • 危险操作默认只做演练（dry-run），要显式确认才真跑

  • 凭据落本地、输出里打码

  • 每一步的产出都能看见，不是黑箱给你一个"完成"了事

能力要强，但每一刀都得能收回来。

最后

回到开头那个体验。

"它答得很好，但活还是我自己干"——这句话的门槛，其实不在模型，而在中间那层壳。

把壳做对了，AI 才从"会聊天的顾问"变成"能把事做完的同事"。

这篇文章本身就是它写、它排版、它发布的。工具链跑通了，剩下的就是你想让它做什么。
